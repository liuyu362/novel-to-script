# 剧本 YAML Schema 设计文档

> 本文档定义 Novel-to-Script 工具使用的剧本 YAML Schema（当前版本 v2.1），并详细说明每个设计决策的背后原因。

---

## 一、为什么选择 YAML？

### 1.1 对比其他格式

| 格式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **YAML** | 可读性强、支持注释、层级自然 | 缩进敏感 | **剧本初稿、人工编辑** |
| JSON | 解析快、工具链成熟 | 无注释、引号噪声大 | API 传输、机器消费 |
| XML | 结构化强、命名空间 | 极其冗长、人工编辑痛苦 | 出版级专业流程 |
| Fountain | 剧本行业标准 | 工具链小、中文支持弱 | 专业编剧出品 |

### 1.2 设计决策

**选择 YAML 作为核心交换格式。**

原因：
1. **初稿需要大量人工打磨** — YAML 的可读性让作者能直接编辑，不需要专业编剧软件
2. **支持注释** — 作者可以在 YAML 中写 `# 此处需加强冲突`，迭代时保留思路
3. **LLM 友好** — YAML 是 LLM 训练数据中的常见格式，生成质量高于随意文本
4. **可双向解析** — `yaml_parser.py` / `yaml_validator.py` 保证 round-trip 可靠性

## 二、完整 Schema 定义（v2.1）

```yaml
# ============================================================
# 剧本 YAML Schema v2.1
# 设计原则：面向剪辑思维，而非小说叙事思维
# ============================================================

元信息:
  标题: "夜影迷局（剧本）"          # 自动生成，格式：原名（剧本）
  原著作: "张三"                     # 从小说元数据提取
  版本: "电影版"                     # 电影版 | 电视剧版 | 舞台剧版
  总场景数: 38                       # 自动统计
  角色数量: 12                       # 自动统计
  生成时间: "2026-06-06T14:30:00+08:00"

角色列表:
  - 编号: 1
    姓名: "林夜"
    别名: ["夜哥", "林警官"]         # 小说中不同称呼，剧本中统一
    性别: "男"
    年龄: "32岁"
    角色类型: "主角"                 # 主角 | 配角 | 反派 | 路人
    描述: "刑警队副队长，冷静敏锐，左眉骨有一道旧疤"
    首次出场: 3                      # 场景编号

场景列表:
  - 编号: 1
    场景标题行: "内景. 滨海市租界旧仓库 - 夜"   # v2.1 新增：标准 Slugline
    名称: "案发现场初勘"
    地点: "滨海市租界旧仓库"
    时间: "Night"
    天气: "暴雨"
    出场角色: ["林夜", "苏晴"]
    转场: "切至"                     # v2.1 新增：转场标记
    入场: ["林夜 从左侧进入"]        # v2.1 新增：角色入场方式
    退场: ["苏晴 从右侧离开"]        # v2.1 新增：角色退场方式
    内容:
      - 类型: "动作"
        景别: "中景"                 # v2.1 新增：镜头景别
        角度: "平视"                 # v2.1 新增：镜头角度
        运动: "固定"                 # v2.1 新增：镜头运动
        文本: "林夜蹲下，手套拂过泥地上的血迹。手电光柱切进雨幕。"
        角色: "林夜"
        情绪: "专注"
        备注: "雨声贯穿整场，台词需与雨声竞争"

      - 类型: "对白"
        景别: "近景"
        角度: "平视"
        运动: "固定"
        文本: "死亡时间不超过六小时。伤口有生活反应，是生前伤。"
        角色: "苏晴"
        情绪: "平静"

      - 类型: "导演指示"
        文本: "[闪回] 血迹特写 → 快速切换 → 林夜抬眼"
        备注: "全片核心悬念的第一次暗示"
```

## 三、字段设计原因

### 3.1 顶层结构：`元信息` + `角色列表` + `场景列表`

**原因：剧本 ≠ 小说，核心是「场景」而非「章节」。**

小说按章节推进，注重叙述节奏；剧本按场景推进，注重**空间转换**和**镜头逻辑**。

顶层三段式结构让：
- 导演/制片快速评估体量（`总场景数` → 几天能拍完）
- 选角团队直接从 `角色列表` 获取完整人物小传
- 场务按 `地点` 聚合场景，制定拍摄计划

---

### 3.2 `元信息.版本`

```yaml
版本: "电影版"   # 电影版 | 电视剧版 | 舞台剧版
```

**原因：同一故事，三种剧本写法完全不同。**

| 版本 | 场景密度 | 对白风格 | 适用 |
|------|----------|----------|------|
| 电影版 | 高 | 精炼、潜台词丰富 | 120分钟院线电影 |
| 电视剧版 | 中 | 直白、冲突外放 | 40集×45分钟 |
| 舞台剧版 | 低 | 口语化、适合台词表演 | 剧场演出 |

LLM 根据版本使用不同的 Prompt 模板（`version_prompts.py`），控制故事节奏和场景密度。

---

### 3.3 `角色列表` 字段

#### 为什么需要 `别名`？

```yaml
别名: ["夜哥", "林警官"]
```

**原因：小说用不同称呼塑造亲密感/尊卑关系，剧本需要统一称呼。**

剧本中一个角色应该只有一个名字（方便场记和演员），但小说中「林夜」「夜哥」「林警官」可能是同一人。`character_extractor.py` 负责合并别名，输出统一角色卡。

#### 为什么需要 `角色类型`？

```yaml
角色类型: "主角"   # 主角 | 配角 | 反派 | 路人
```

**原因：指导 LLM 生成剧本时的戏份分配。**

- `主角` 的戏份应占 60-70%，每个场景都要问「这场有没有主角？」
- `反派` 需要专门的对抗场景，不能与主角同时出场却无交集
- `路人` 在剧本中通常不需要完整对白，一句动作描述即可

#### 为什么需要 `首次出场`？

```yaml
首次出场: 3   # 场景编号
```

**原因：小说可以用大量篇幅铺垫后主角才登场，但剧本通常前10场必须建立主角。** 这个值让 `logic_checker.py` 能检测「主角出场太晚」的改编问题。

---

### 3.4 `场景列表` 字段

#### 为什么需要 `地点`？

```yaml
地点: "滨海市公安局审讯室"
```

**原因：这是制片排程的核心维度。** 拍摄不是按场景编号顺序拍，而是按**地点聚合**拍——所有「审讯室」场景同一天拍完，无论编号是 2、15 还是 37。

#### 为什么 `时间` 和 `天气` 分开存储？

```yaml
时间: "Night"
天气: "暴雨"
```

**原因：这是两个独立的拍摄约束。**
- `时间`：影响灯光方案（日戏用自然光 vs 夜戏用灯光车）
- `天气`：影响拍摄成本和档期（暴雨夜需等天气或人工降雨）

分开存储让场务能独立排程。

#### 为什么需要 `出场角色` 数组？

**原因：驱动三个后续功能。**
1. **逻辑检测** — 如果场景内容中出现列表外的角色说话 → 人物穿帮
2. **演员档期** — 每个演员的出场场景列表 = 他们的工作日
3. **场景合并建议** — 两个场景的出场角色完全相同且地点相同 → 建议合并

---

### 3.5 `内容.类型`：语义三元组

```yaml
类型: "动作"      # 视觉信息
类型: "对白"      # 听觉信息
类型: "导演指示"  # 元信息
```

**原因：对应影视制作的三条工作流。**

| 类型 | 对应部门 | 例子 |
|------|----------|------|
| `动作` | 摄影 + 美术 | 「他端起杯子」→ 需要道具、演员动作、镜头构图 |
| `对白` | 录音 + 演员 | 「你到底是谁」→ 需要收音、台词表演 |
| `导演指示` | 剪辑 + 导演 | 「[闪回]」「[切特写]」→ 需要后期剪辑 |

LLM 在 `dialogue_separator.py` 中完成这个分类。

#### 为什么需要 `情绪` 字段？

**原因：对白文本本身往往看不出情绪。** 小说可以写「他冷冷地说」，剧本中这是演员指导信息。没有 `情绪`，演员只能靠自己的理解，容易偏离导演意图。

#### 为什么需要 `备注` 字段？

**原因：保留给人类协作者的上下文，不进入正式拍摄。** 小说改编时备注「此处原著第3章对应」，逻辑检测时备注「此场景与第15场有伏笔呼应」。

### 3.6 v2.1 新增：专业拍摄字段

#### 镜头三要素：`景别` / `角度` / `运动`

```yaml
景别: "中景"     # 远景 | 全景 | 中景 | 近景 | 特写 | 大特写
角度: "平视"     # 平视 | 俯视 | 仰视 | 鸟瞰 | 倾斜
运动: "固定"     # 固定 | 推 | 拉 | 摇 | 移 | 跟 | 升降 | 手持
```

**原因：v2.0 的文学剧本只能指导演员，v2.1 的分镜头信息可直接对接摄影组。**

- `景别` 决定构图范围 → 摄影师据此选择焦段
- `角度` 决定画面情绪 → 仰视 = 威严，俯视 = 渺小
- `运动` 决定节奏感 → 手持 = 纪实感，推镜头 = 强调

#### `场景标题行`（Slugline）

```yaml
场景标题行: "内景. 滨海市租界旧仓库 - 夜"
```

**原因：这是专业剧本的行业标准格式。** `内景/外景. 地点 - 时间` 一行概括场景的核心拍摄信息，方便场记快速索引和制片排程。`yaml_validator.py` 能根据地点名称自动判断内景/外景。

#### `转场` 标记

```yaml
转场: "切至"     # 切至 | 淡入淡出 | 淡入 | 淡出 | 叠化 | 划像 | 黑场
```

**原因：转场是剪辑节奏的核心控制。** 小说中场景切换靠章节分隔，剧本中不同的转场方式传达完全不同的情绪：`切至` = 快节奏，`叠化` = 时间流逝，`黑场` = 情绪停顿。

#### `入场` / `退场` 标记

```yaml
入场: ["林夜 从左侧进入"]
退场: ["苏晴 从右侧离开"]
```

**原因：演员的走位信息在剧本中不可或缺。** 入场/退场标记让导演一眼看清每场戏的角色流动方向，直接指导走位排练和舞台调度（blocking）。

## 四、完整性校验规则

`yaml_validator.py` 执行以下校验：

| 规则 | 说明 |
|------|------|
| 场景编号连续 | `编号` 必须从 1 开始连续，不允许跳号 |
| 角色首次出场 ≤ 场景总数 | `首次出场` 不能引用不存在的场景 |
| 出场角色必须在角色列表中 | 不能出现未定义的角色 |
| 对白必须有角色 | `类型: "对白"` 时 `角色` 不能为空 |
| 景别/角度/运动合法性 | 值必须在预设枚举范围内，非法值自动修复 |
| 场景标题行自动生成 | 如未填写，根据地点自动推断内景/外景 |
| Slugline 格式校验 | `内景/外景. 地点 - 时间` |

## 五、总结

| 设计决策 | 原因 |
|----------|------|
| 选 YAML 而非 JSON | 人工可编辑 + 支持注释 + LLM 生成质量高 |
| 顶层三分结构 | 匹配剧组「导演-选角-场务」三条工作流 |
| `版本` 字段 | 同一故事电影/剧/舞台剧写法完全不同 |
| `别名` 合并 | 小说称呼多样 → 剧本需要统一角色名 |
| `内容.类型` 三分法 | 对应影视制作「摄影-录音-剪辑」三条线 |
| `镜头三要素`（v2.1） | 分镜头信息直接对接摄影组 |
| `场景标题行`（v2.1） | 行业标准格式，方便索引和排程 |
| `转场`（v2.1） | 控制剪辑节奏和画面情绪 |
| `入场/退场`（v2.1） | 指导演员走位和舞台调度 |
| `备注` 字段 | 保留改编上下文，不进入正式拍摄流程 |
